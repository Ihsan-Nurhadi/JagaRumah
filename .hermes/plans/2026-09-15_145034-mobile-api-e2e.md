# Nayaka Mobile API E2E Test Plan

> **For Hermes:** Jalankan setiap task satu per satu. Satu test case = satu task/checklist item.

**Goal:** Membuktikan kontrak API mobile Nayaka dari request HTTP sampai response, database, ownership, session, dan efek samping yang dijanjikan.

**Architecture:** Smoke/E2E test memakai HTTP ke server Next.js yang sedang berjalan, database Supabase nyata untuk fixture aman, dan Mailtrap hanya diuji bila credential sudah tersedia. Credential, password, token, reset code, dan email uji tidak boleh ditulis ke log atau repository.

**Tech Stack:** Next.js Route Handlers, PostgreSQL/Supabase, curl/Bun atau Node test runner, `.env` server.

---

## Aturan eksekusi

- Target lokal default: `http://127.0.0.1:3101`.
- Target Vercel diisi eksplisit ketika menguji deployment.
- Semua request mobile memakai `Content-Type: application/json` bila memiliki body.
- Response dicek berdasarkan status HTTP, envelope, `meta.request_id`, field payload, dan tidak adanya secret.
- Test positif yang membuat data wajib memakai prefix fixture unik dan dibersihkan setelah test.
- Jangan memakai customer/admin nyata.
- Jika tidak tersedia fixture aman, tandai `UNVERIFIED`, jangan membuat credential sembarang.
- Test Mailtrap tidak boleh menganggap HTTP `200` sebagai bukti email terkirim; bukti delivery harus dicek di Inbox Mailtrap.

## Fixture dan cleanup

Sebelum test flow authenticated:

1. Generate `RUN_ID` lokal tanpa mencetak credential.
2. Buat satu customer fixture lewat register dengan email unik.
3. Simpan token hanya di environment proses test, bukan file repo/log.
4. Setelah suite, logout-all dan hapus fixture melalui SQL cleanup yang scoped ke email prefix test.
5. Jangan menghapus data yang tidak dibuat oleh run tersebut.

File yang disarankan:

- Create: `scripts/verify/uji-mobile-e2e.ts`
- Optional SQL cleanup: `/tmp/nayaka-mobile-cleanup.sql` atau file lokal yang tidak di-commit
- Contract reference: `MOBILE_API_Contract.md`

## Test cases

### Task 1: Register dengan payload valid

**Request:** `POST /api/v1/mobile/auth/register`

**Input:** `full_name`, email fixture unik, password valid, `installation_id`, `platform`, `app_version`.

**Expected positive:**

- HTTP `201`.
- Body memiliki `data.access_token`, `data.refresh_token`, `data.token_type = "Bearer"`, `data.expires_in`.
- `data.customer.email` sama dengan email normalized.
- `meta.request_id` berupa string.
- Body tidak memuat password atau token hash.
- Row customer, auth account provider `email`, dan session terbentuk.

**Negative assertions:** Tidak boleh HTTP `200`, tidak boleh `onboarding_required` bernilai salah, dan tidak boleh ada raw SQL/error provider.

**Cleanup:** Simpan customer fixture ID untuk cleanup suite.

---

### Task 2: Register menolak payload malformed

**Request:** `POST /api/v1/mobile/auth/register`

**Input:** `{}` dan payload dengan email invalid, platform invalid, password terlalu lemah/pendek.

**Expected:**

- HTTP `400`.
- `error.code = VALIDATION_ERROR`.
- `error.details.fields` menunjuk field yang salah.
- Tidak ada customer, auth account, atau session yang dibuat.

---

### Task 3: Register menolak email duplikat

**Request:** `POST /api/v1/mobile/auth/register`

**Input:** Email customer fixture yang sudah ada.

**Expected:**

- HTTP `409`.
- `error.code = EMAIL_ALREADY_REGISTERED`.
- Tidak ada customer kedua.
- Tidak ada password atau database error mentah dalam response.

---

### Task 4: Login dengan credential valid

**Request:** `POST /api/v1/mobile/auth/login`

**Input:** Email/password fixture valid dan metadata installation valid.

**Expected:**

- HTTP `200`.
- Access token dan refresh token baru dikirim.
- Customer payload benar.
- `last_login_at` berubah.
- Session baru tersimpan dengan refresh token hash, bukan token plaintext.

---

### Task 5: Login menolak password salah secara generik

**Request:** `POST /api/v1/mobile/auth/login`

**Input:** Email fixture benar, password salah.

**Expected:**

- HTTP `401` atau `429` bila rate limit sudah aktif.
- Normalnya `error.code = INVALID_CREDENTIALS`.
- Pesan tidak membedakan password salah dan email tidak terdaftar.
- Tidak ada token yang diterbitkan.

---

### Task 6: Login menolak email tidak terdaftar secara generik

**Request:** `POST /api/v1/mobile/auth/login`

**Input:** Email non-existent dan password valid-format.

**Expected:**

- HTTP `401` atau `429`.
- Response code/pesan tidak membocorkan account existence.
- Bentuk error dibandingkan dengan Task 5 untuk memastikan tidak enumerable.

---

### Task 7: Refresh merotasi refresh token

**Request:** `POST /api/v1/mobile/auth/refresh`

**Input:** Refresh token hasil login dan `installation_id` yang sama.

**Expected:**

- HTTP `200`.
- Access token dan refresh token baru berbeda dari token lama.
- Token lama tidak dapat dipakai ulang.
- Session lama revoked dan menunjuk session pengganti.

---

### Task 8: Refresh menolak token reuse

**Request:** `POST /api/v1/mobile/auth/refresh`

**Input:** Refresh token lama setelah Task 7.

**Expected:**

- HTTP `401`.
- `error.code = TOKEN_REVOKED`.
- Tidak dibuat session baru akibat reuse.

---

### Task 9: Protected endpoint menolak tanpa bearer token

**Request:** `GET /api/v1/mobile/me` atau `GET /api/v1/mobile/dashboard` tanpa Authorization.

**Expected:**

- HTTP `401`.
- Tidak ada query data customer yang dikirim.
- Response memiliki error envelope dan `request_id`.

---

### Task 10: Protected endpoint menolak bearer token invalid/expired

**Request:** `GET /api/v1/mobile/me` dengan token random atau token expired.

**Expected:**

- HTTP `401`.
- Code `TOKEN_EXPIRED` atau code yang ditetapkan implementation untuk token invalid.
- Tidak ada data profile/dashboard.

---

### Task 11: Get profile dengan token valid

**Request:** `GET /api/v1/mobile/me`

**Expected:**

- HTTP `200`.
- Profile hanya customer dari token.
- Email, status, subscription sesuai DB fixture.
- Tidak ada password hash, refresh hash, atau data customer lain.

---

### Task 12: Patch profile hanya field yang diizinkan

**Request:** `PATCH /api/v1/mobile/me`

**Input:** `full_name` dan `avatar_url` valid.

**Expected:**

- HTTP `200`.
- Nilai berubah di DB dan response.
- `email`, `status`, dan subscription tidak berubah.

---

### Task 13: Patch profile menolak payload invalid/field sensitif

**Request:** `PATCH /api/v1/mobile/me`

**Input:** URL avatar invalid, body kosong, atau percobaan mengubah `status`/`email`.

**Expected:**

- HTTP `400` untuk payload malformed.
- Tidak ada perubahan tidak sah.
- Field sensitif tidak boleh diterima secara diam-diam.

---

### Task 14: Forgot password payload malformed

**Request:** `POST /api/v1/mobile/auth/forgot-password`

**Input:** `{}`, email invalid, atau body bukan JSON.

**Expected:**

- HTTP `400`.
- `error.code = VALIDATION_ERROR`.
- Tidak ada mail attempt untuk payload invalid.

---

### Task 15: Forgot password untuk email tidak terdaftar aman dari enumeration

**Request:** `POST /api/v1/mobile/auth/forgot-password`

**Input:** Email non-existent syntactically valid.

**Expected:**

- HTTP `200`.
- Body sama bentuk dan nilai dengan email valid, yaitu `sent: true` dan `expires_in: 900`.
- Tidak ada reset row atau email yang benar-benar dikirim.
- Waktu/error tidak membocorkan keberadaan akun.

---

### Task 16: Forgot password untuk email valid membuat reset record dan mengirim Mailtrap

**Request:** `POST /api/v1/mobile/auth/forgot-password`

**Input:** Email customer fixture.

**Prerequisite:** `MAILTRAP_SMTP_USERNAME` dan `MAILTRAP_SMTP_PASSWORD` tersedia; Inbox Mailtrap bisa diakses.

**Expected:**

- HTTP `200` dengan response generik.
- Reset record tersimpan sebagai hash, purpose `reset_password`, expiry sekitar 15 menit.
- Reset code tidak muncul di response/log/database plaintext.
- Email terlihat di Inbox Mailtrap dengan recipient yang benar.

**Jika credential kosong:** tandai `UNVERIFIED`, jangan mengubah env atau mengklaim delivery.

---

### Task 17: Reset password menolak code invalid

**Request:** `POST /api/v1/mobile/auth/reset-password`

**Input:** Email fixture, code 6 digit salah, password baru valid.

**Expected:**

- HTTP `422`.
- `error.code = INVALID_VERIFICATION_CODE`.
- Attempt count bertambah.
- Password dan session tidak berubah.

---

### Task 18: Reset password valid mengonsumsi code dan mencabut session

**Request:** `POST /api/v1/mobile/auth/reset-password`

**Input:** Code asli yang diperoleh hanya dari Mailtrap Inbox, password baru valid.

**Expected:**

- HTTP `204`.
- Reset row memiliki `consumed_at`.
- Password baru bisa dipakai login.
- Semua session lama customer revoked.
- Code yang sama tidak bisa digunakan lagi.

**Security:** Jangan menulis code ke test output.

---

### Task 19: Reset password code reuse ditolak

**Request:** Ulangi request Task 18 dengan code yang sama.

**Expected:**

- HTTP `422`.
- Code `VERIFICATION_EXPIRED`, `INVALID_VERIFICATION_CODE`, atau code implementasi yang sesuai kondisi consumed.
- Password tidak berubah lagi.

### Task 28: CORS/content-type/request-id contract

**Request:** Jalankan request normal, body malformed, dan method tidak didukung.

**Expected:**

- JSON response konsisten.
- `meta.request_id` atau `error.request_id` selalu ada.
- Content type response sesuai JSON kecuali `204`.
- Tidak ada stack trace/SQL/raw provider error.

---

### Task 29: Rate limit authentication paths

**Request:** Kirim percobaan login/forgot/reset berulang pada batas aman test environment.

**Expected:**

- Setelah threshold, HTTP `429` dan error code `RATE_LIMITED`, `AUTH_RATE_LIMITED`, atau code yang dikontrak.
- Ada `Retry-After` jika implementasi menjanjikannya.
- Test tidak membebani production; jalankan hanya dengan batas dan fixture khusus.

**Open check:** Saat ini rate limit disebut di kontrak/security rules tetapi harus diverifikasi apakah implementasinya sudah tersedia di route mobile.

## Verification command sequence

1. `git diff --check`
2. `bash /tmp/nayaka-typecheck.sh`
3. `pnpm lint`
4. `pnpm db:verify`
5. Jalankan server target.
6. Jalankan setiap test case sebagai satu task/checklist item.
7. Simpan ringkasan status `PASS`, `FAIL`, atau `UNVERIFIED` tanpa credential.
8. Cleanup fixture.
9. Ulangi smoke subset terhadap URL Vercel setelah deployment tersedia.

## Output format hasil

```text
T01 register valid                 PASS
T02 register malformed             PASS
T03 duplicate email                PASS
...
T16 Mailtrap delivery              UNVERIFIED (SMTP env kosong)
...
Summary: 25 PASS, 1 FAIL, 2 UNVERIFIED
```

## Risiko dan batasan

- Happy path reset password membutuhkan code asli dari Mailtrap; jangan dipalsukan.
- Authenticated test membutuhkan fixture customer aman.
- HTTP `401` hanya membuktikan guard, bukan query happy path.
- Test lokal tidak membuktikan latency Vercel. Ulangi subset di deployment.
- Serverless cold start, region Vercel, Supabase latency, dan SMTP latency harus dicatat terpisah.
